# Sikka 1.0 Node benchmark leadership protocol

**Decision scope.** This protocol defines the evidence required to say “Sikka is #1 overall in Sikka’s official Node.js benchmark.” It is a release-gate proposal for [issue #5](https://github.com/ws-rush/sikka/issues/5), not an implementation change. It covers Node only; no other runtime contributes to the ranking.

## Observed suite (commit `19bc591`)

- `bench/index.js` benchmarks the **precompiled render** phase for eight engines over four equally weighted scenarios: static HTML, escaped interpolation, a conditional/attribute, and nested loops. It compiles outside timing and validates each renderer once against a literal expected HTML string before timing. [Runner](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/bench/index.js)
- It invokes Tinybench with `throws: true`, 1,000 ms measurement and 250 ms warmup defaults (both environment-overridable); it prints mean throughput and Tinybench RME. Tinybench also enforces at least its default 64 iterations, so `time` is not a fixed iteration count. [Runner](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/bench/index.js) · [Tinybench options](https://github.com/tinylibs/tinybench/blob/main/src/types.ts#L152-L298) · [run loop](https://github.com/tinylibs/tinybench/blob/main/src/task.ts#L420-L426)
- The displayed overall score is the geometric mean of each scenario’s mean-throughput ratio to that scenario’s fastest engine. This makes all four scenarios equal-weighted, but it does not combine uncertainty, repeat processes, or establish a statistically defensible winner. [Scoring code](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/bench/index.js)
- It reports Node version, first CPU model, OS/architecture, scenario results, and rank, calls `globalThis.gc?.()` between scenarios, and the npm script supplies `--expose-gc`. It does not record Node binary checksum, OS/kernel, CPU topology/governor, commit, dependency resolutions, command/options, raw samples, or repeated runs. [Runner](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/bench/index.js) · [npm script](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/package.json)
- Root dependencies (including Tinybench) use semver ranges; there is no tracked Node-version file or benchmark dependency manifest/lockfile. `benchmark/` is ignored even though the runner resolves `../benchmark/package.json` and the README instructs `npm ci --prefix benchmark`; this isolated checkout therefore cannot reproduce the declared setup. [Manifest](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/package.json) · [ignore rule](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/.gitignore) · [README](https://github.com/ws-rush/sikka/blob/19bc5915c5c7ac340d52e3a4e51fc4535f163980/README.md#L145-L160).

## Required protocol and release-gate inputs

1. **Pin the runtime at the gate.** On the gate date, select the highest released patch of the highest Node major whose `lts` field is non-false in Node’s official distribution index; at this research access date it resolves to Node `v24.18.1` (Krypton, released 2026-07-28). Record the resolved `vX.Y.Z`, release date, platform/architecture, and official `SHASUMS256.txt` digest. Put that exact version in the tracked benchmark environment (rather than treating “latest LTS” as an unrecorded moving target). Re-evaluate the selector for each release candidate; a newer LTS means a new baseline, not permission to reuse an old claim. Node’s release schedule defines the LTS lifecycle, and its distribution index is the primary machine-readable release inventory. [Node release schedule](https://github.com/nodejs/Release/blob/main/schedule.json) · [Node distribution index](https://nodejs.org/dist/index.json) · [checksums](https://nodejs.org/dist/latest/SHASUMS256.txt).

2. **Freeze the field.** Before measurements, approve a named competitor list and exact npm versions. Commit a benchmark-only `package.json` and lockfile with registry integrity data; install with the lockfile’s immutable-install command. Record the resolved package name/version/integrity for Sikka, Tinybench, and every engine (including transitive resolution), plus the adapter configuration and template source. Changing an engine, version, adapter, scenario, Node patch, Tinybench version, or scoring rule creates a new benchmark revision and invalidates comparison with earlier results.

3. **Prove rendered-HTML equivalence before timing.** Keep compilation and file I/O outside the measured render phase for every engine. For every approved scenario, run a deterministic equivalence suite before every measured process: exact byte-for-byte output must equal the fixture’s canonical expected HTML for every engine. Expand inputs to both conditional outcomes, empty and multi-item loops, attribute escaping, and strings containing HTML-significant characters; include each template and expected output in the revision. A mismatch, throw, async completion failure, or unavailable engine is a failed gate, not an omitted row. This preserves the ticket’s “every engine produces identical HTML” condition rather than rewarding a faster different workload.

4. **Use Tinybench deliberately, then repeat whole processes.** Keep tasks serial (`concurrency: null`) and fail on exceptions. Set explicit, version-pinned warmup time/iterations and measurement time/minimum iterations; use a release setting materially longer than the quick-feedback defaults (for example, 1 s warmup and 5 s measured time per task), not environment overrides. Tinybench warms each task separately and measures until *both* duration and minimum iterations are satisfied. [Tinybench task implementation](https://github.com/tinylibs/tinybench/blob/main/src/task.ts#L325-L338) · [measurement condition](https://github.com/tinylibs/tinybench/blob/main/src/task.ts#L420-L426). Run at least five fresh Node processes on an otherwise idle, fixed machine; retain/export the per-task samples and complete per-process results. Do not cherry-pick a favorable run.

   Treat Tinybench RME as a diagnostic, not proof of cross-process superiority: Tinybench computes it from the sample standard error and a Student-t critical value for a task’s mean. [Tinybench statistics](https://github.com/tinylibs/tinybench/blob/main/src/utils.ts#L642-L677). Predeclare an acceptance limit (recommended: RME <= 5% for every task in every retained run); rerun an invalid/noisy trial once, then fail and investigate if it remains above the limit. Also fail on Tinybench timer-saturation warnings rather than silently accepting timer-dominated samples. [Tinybench warning reasons](https://github.com/tinylibs/tinybench/blob/main/src/types.ts#L747-L759).

5. **Make “overall #1” falsifiable.** For each successful process, calculate the existing equal-weight geometric mean from that process’s scenario mean throughputs; do not average individually rounded console values. Report each engine’s five process-level scores and the median score. The gate passes only when Sikka has the highest median **and** wins in at least four of five process-level overall rankings. Publish the runner-up margin and all scenario medians alongside the rank. A tie, a margin smaller than the observed process-to-process spread, failed equivalence, missing comparator, or RME failure must be reported as “no defensible #1 claim,” not rounded up to #1. The geometric mean is appropriate here only because the scenario set and equal weighting are declared in advance; it is not a universal product-performance score.

6. **Capture a rerunnable evidence bundle.** Publish an immutable artifact per gate run containing: repository commit and dirty status; benchmark revision/fixture hashes; exact command and environment variables; Node version and binary digest; package manager version and lockfile digest; resolved dependency list; Tinybench version/options/timestamp provider; CPU model/core count, RAM, OS/kernel, architecture, power/governor setting where available; raw process output, raw samples, and the unrounded calculation table. State whether the machine was dedicated/idle and whether network/background services were disabled. Include the exact artifact URL in release notes, with the narrowly scoped wording “#1 overall under benchmark revision R on Node vX.Y.Z and the recorded host,” not a general “fastest template engine” claim.

## Release decision inputs

The release owner must approve, before optimization or gating: (a) the competitor inclusion rule and exact initial list, (b) the benchmark revision and fixture corpus, (c) explicit timing/iteration/RME values, (d) the dedicated host or CI runner identity, (e) the five-process median and win-count rule above, and (f) the claim wording. These inputs prevent the suite owner from changing the field, workload, or statistical standard after seeing a result.
