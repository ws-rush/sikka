# Sikka’s fixed Astro-derived subset: semantic matrix

**Issue:** [#11](https://github.com/ws-rush/sikka/issues/11)
**Decision applied:** [#6](https://github.com/ws-rush/sikka/issues/6)
**Scope:** only constructs illustrated in `README.astro-syntax.md`. This is a 1.0 contract/research handoff, not a proposal to implement more Astro.

## Reading this matrix

Each rule separates:

- **Astro fact** — a directly cited statement or observable implementation/test in Astro’s official docs/source.
- **Sikka 1.0 contract** — exact wording and conformance assertion required by #6 and Sikka’s already documented subset. This is the rule Sikka must document and test; it is not a promise to add non-subset Astro functionality.
- **Outside the subset** — related Astro capability that must not silently enlarge Sikka 1.0.

Local context used: `README.astro-syntax.md`, `docs/UBIQUITOUS_LANGUAGE.md`, and the prior [syntax-contract audit](sikka-1-syntax-contract-audit.md). The audit establishes current behavior/gaps; Astro sources below establish only the facts explicitly attributed to Astro.

## 1. Attributes, spreads, and directives

| Construct | Astro fact | Sikka 1.0 contract and conformance assertion | Outside the fixed subset |
| --- | --- | --- | --- |
| Native HTML attribute values | Astro documents that HTML-element attributes are converted to strings, while Component attributes are Props. Its SSR runtime omits `null`/`undefined`; renders standard boolean attributes only when truthy; stringifies ordinary `false` and `0`; and treats an empty string as a valueless attribute. [Syntax reference](https://docs.astro.build/en/reference/astro-syntax/#dynamic-attributes), [SSR attribute source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/render/util.ts), [attribute tests](https://github.com/withastro/astro/blob/main/packages/astro/test/units/app/astro-attrs.test.ts) | For a native or custom HTML tag: `null`/`undefined` omit the attribute; a standard HTML boolean is present iff truthy; other values stringify (`false` → `"false"`, `0` → `"0"`); and `""` emits a valueless attribute. Test all four values for `disabled` and `data-x`. Escaping applies to emitted attribute values unless `autoEscape: false`. | Astro’s complete HTML-attribute catalog and special framework hydration attributes are not adopted merely by this rule. |
| Custom elements | Astro’s SSR source identifies a custom element by `-` in its name and renders even boolean-looking values as string attributes rather than HTML boolean attributes. [SSR attribute source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/render/util.ts), [custom-element test](https://github.com/withastro/astro/blob/main/packages/astro/test/dev-render-components.test.ts) | A hyphenated static tag is native/custom-element output, not a Sikka Component. Preserve its `slot` attribute as HTML. Test `<my-toggle selected={false}/>` contains `selected="false"`; it does not use native boolean omission. | Browser custom-element registration, shadow DOM, and client behavior are not Sikka features. |
| Spread order and collisions | Astro’s compiler preserves source-order output positions for literal attributes and spreads; its spread runtime enumerates the supplied object and applies normal attribute conversion. The retrieved primary source does **not** establish one general, public Astro rule for a collision between an ordinary direct attribute and an ordinary spread key. [compiler snapshots](https://github.com/withastro/compiler/tree/main/internal/printer/__printer_js__), [spread runtime](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/index.ts) | Make the subset deterministic: evaluate attributes and spreads left-to-right into one attribute record; later entries replace earlier entries for the same ordinary key. Thus `<div {...p} id="x"/>` has `id="x"`, and `<div id="x" {...p}/>` uses `p.id` (or omits it when nullish). Test both, plus multiple spreads. This is required Sikka contract wording, not an Astro fact inferred beyond the cited source. | Do not claim full JSX/DOM property-spread compatibility. |
| `class`, `class:list`, and `style` | Astro compiles literal `class` plus `class:list` as one class-list value and its runtime normalizes `class:list` into `class`; official tests cover both textual orders and a spread case. Its SSR attribute helper also recognizes a spread `class:list` key. `class:list` uses `clsx` semantics: strings included; truthy object keys included; arrays flattened; false/null/undefined skipped. Style objects kebab-case ordinary keys, retain CSS variables, include numbers (including `0`), and omit nullish/boolean/empty values. [directive docs](https://docs.astro.build/en/reference/directives-reference/#classlist), [compiler snapshots](https://github.com/withastro/compiler/tree/main/internal/printer/__printer_js__), [SSR attribute source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/render/util.ts), [tests](https://github.com/withastro/astro/blob/main/packages/astro/test/units/render/class-list-and-style.test.ts) | Emit one `class` attribute, merging `class`, `className`, and direct or spread `class:list` in source order; do not deduplicate class tokens. A direct `style` object serializes as documented above; direct `style` string plus object concatenate in source order with `;`. Test `class="x" class:list={['y', false]}` → `class="x y"`, `{...{'class:list': ['a']}}` → `class="a"`, `style="margin:0" style={{padding: 0}}` → `style="margin:0;padding:0"`, and no class for an all-falsy `class:list`. | Astro CSS scoping/injected scope classes and its framework-specific style behavior are out. |
| Directives in a spread | Astro requires a directive to be visible to the compiler and explicitly says `<X {...attr}>` cannot supply one. Its SSR runtime specially supports a spread `class:list` key, but warns/ignores dynamically spread `set:html`/`set:text`; it does not turn the latter into directives. [directive rules](https://docs.astro.build/en/reference/directives-reference/#rules), [SSR attribute source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/render/util.ts) | The documented `class:list` spread is the one fixed exception and follows the preceding row. A spread key named `set:html`, `set:text`, or `is:raw` is a compile diagnostic, not an emitted attribute and not directive behavior. Test each key. This supersedes the reference’s illustrative spread-`set:html` example. | `client:*`, `server:*`, `define:vars`, `is:global`, and custom directives are not adopted. `is:inline` is intentionally rejected with a diagnostic under #6. |
| `set:html`, `set:text`, and `is:raw` | Astro documents `set:html` as unescaped `innerHTML`-like insertion (including on `Fragment`) and `set:text` as escaped/direct-expression-equivalent insertion. `is:raw` makes its children text, so Astro syntax inside is ignored. [directive docs](https://docs.astro.build/en/reference/directives-reference/#sethtml), [set:text](https://docs.astro.build/en/reference/directives-reference/#settext), [is:raw](https://docs.astro.build/en/reference/directives-reference/#israw) | `set:html` is Sikka’s only template-level Raw HTML mechanism and carries an XSS/trust warning; `set:text` escapes; `is:raw` preserves its source children as text. Direct `set:html`/`set:text` conflicts and either directive with children are diagnostics; `Fragment` permits only documented `slot`, `set:html`, and `set:text` uses. Test raw versus escaped `<b>x</b>` and every listed conflict. Sikka exposes no public `RawHtml` wrapper. `autoEscape: false` is the documented global opt-out for normal escaped output, never a substitute for the explicit `set:html` trust boundary. | Astro also accepts `Promise<string>`/`Promise<Response>` for `set:html`; that is not a documented Sikka feature and must not be added by implication. |

## 2. Slots

| Construct | Astro fact | Sikka 1.0 contract and conformance assertion | Outside the fixed subset |
| --- | --- | --- | --- |
| Default and named assignment | Astro sends unslotted children (and `slot="default"`) to the default slot; immediate children with `slot="name"` go to the matching named slot, and multiple matching children render in order. Named slots must be immediate children. [Astro Components: slots](https://docs.astro.build/en/basics/astro-components/#slots) | A Component receives Props separately from its Slots. Collect immediate children by `slot`; concatenate matching children in source order; a no-`slot` child is default. Unused supplied Slots render nothing. Test two named children, interleaved default children, and an unused named Slot. | Slot APIs/function children, UI-framework slot interop, and nested-element forwarding are out. |
| Presence and fallback | Astro renders fallback only with no matching supplied slot. Its docs explicitly say an existing but empty passed slot suppresses fallback. [fallback documentation](https://docs.astro.build/en/basics/astro-components/#fallback-content-for-slots), [runtime source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/render/slot.ts) | Slot **presence**, not rendered byte length, decides fallback. Any supplied matching child—an empty `Fragment`, `null`, `undefined`, `""`, or whitespace—installs the Slot and suppresses fallback. Only an absent matching Slot renders Fallback content. Test the absent case and each listed present-but-empty case. The null/empty-expression list is a necessary explicit Sikka assertion; Astro’s prose establishes the empty-slot principle but does not enumerate those expression forms. | `Astro.slots.has()`/`.render()` are not part of the documented Sikka subset. Astro’s async `Astro.slots.render()` is therefore not adopted. |
| Dynamic names | Astro documentation says Astro slot names cannot be dynamically generated. [named-slot limitation](https://docs.astro.build/en/basics/astro-components/#named-slots) | `README.astro-syntax.md` already illustrates `name={name}` and `slot={name}`. Under #6’s fixed documented scope, Sikka keeps those forms: evaluate the expression during the Render and match by the resulting string. Test dynamic producer and receiver names. This is an explicit Sikka divergence, not an Astro compatibility claim. | Do not generalize this to Astro’s framework slots, map-generated slot declarations, or additional slot APIs. |
| Forwarding | Astro documents forwarding a named Slot with both attributes: `<slot name="head" slot="head" />`; default slots forward with `<slot />`. [slot transfer documentation](https://docs.astro.build/en/basics/astro-components/#transferring-slots) | `<slot name="x" slot="y"/>` forwards the received `x` Slot to child Component Slot `y` without rendering a wrapper. `<slot/>` forwards default content. If `x` is absent, the child sees `y` absent and its Fallback content applies. Test named forwarding, default forwarding, and absent forwarding. | Framework-component slot transport and server-island fallback Slots are out. |

## 3. Components, tags, expressions, and raw output

| Construct | Astro fact | Sikka 1.0 contract and conformance assertion | Outside the fixed subset |
| --- | --- | --- | --- |
| Component vs native tag | Astro Components receive attributes as Props; native attributes stringify. Astro dynamic tags require a capitalized variable name; lowercase is rendered as a literal HTML tag name. [component Props](https://docs.astro.build/en/basics/astro-components/#component-props), [dynamic tags](https://docs.astro.build/en/reference/astro-syntax/#dynamic-tags) | A registered/imported capitalized tag is a Component: attributes are Props and children are Slots. A lowercase static tag and a hyphenated custom tag are emitted HTML. A capitalized dynamic tag evaluates its binding: a Component value composes; a string value emits that tag. A lowercase `<tag>` never resolves the `tag` binding. Test each category. | Framework components, hydration, built-in dynamic-component utilities, and arbitrary unresolved capitalized identifiers are not a new Sikka feature. The primary docs do not establish an Astro rule for Sikka’s current unknown-capitalized-tag fallback; do not specify it here as Astro compatibility. |
| Expression rendering | Astro documents JSX-like expressions, conditionals, and mapping. Its documented `set:html` contrast establishes that a direct expression escapes markup. The retrieved Astro documentation/source does not define a public, exhaustive template rule for every JavaScript value (for example arbitrary plain objects and functions). [expressions](https://docs.astro.build/en/reference/astro-syntax/#dynamic-html), [raw-output contrast](https://docs.astro.build/en/reference/directives-reference/#sethtml) | Sikka must make its documented examples exact: recursively flatten arrays; omit `null`, `undefined`, `true`, and `false`; stringify numbers (including `0`, `NaN`, infinities, `-0`, and BigInt), objects, and functions with JavaScript string conversion; then HTML-escape normal expression output. `0 && <X/>` therefore emits `0`. Test every listed class and a string containing `<>&\"'`. This is a required fixed Sikka contract where Astro primary material is not exhaustive. | React/JSX runtime semantics, reactivity, and unlisted JavaScript/TypeScript transformations are out. |
| Escaping and Raw HTML | Astro’s documented contrast is `{html}` → escaped text and `set:html={html}` → parsed unescaped HTML; `set:text` is escaped. Astro’s internal branded HTML string is not a documented public API. [directive docs](https://docs.astro.build/en/reference/directives-reference/#sethtml), [Astro internal escape source](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/server/escape.ts), [Astro export map](https://github.com/withastro/astro/blob/main/packages/astro/package.json) | Escape normal Expressions and `set:text` by default. `set:html` alone inserts trusted Raw HTML. `autoEscape: false` remains Sikka’s documented global application opt-out, with a security warning, and applies consistently to normal expression/attribute/text emission in both render modes. No public `RawHtml` API exists. Test default escaping, explicit `set:html`, and `autoEscape: false` independently. | Public internal Astro `HTMLString`/`markHTMLString` compatibility is not adopted. |

## 4. Frontmatter and render modes

| Construct | Astro fact | Sikka 1.0 contract and conformance assertion | Outside the fixed subset |
| --- | --- | --- | --- |
| Frontmatter scope/imports | Astro frontmatter is server-side TypeScript and permits arbitrary component/framework/data imports, fetching, and top-level `await`. [component script documentation](https://docs.astro.build/en/basics/astro-components/#the-component-script) | Sikka Frontmatter is a small Template setup area: Props access, local constants/helpers, and **Component-only** `.astro` imports used in composition. A non-Component/application-module import is a clear diagnostic. Test a default `.astro` import succeeds and `import data from './data.js'` fails. | Astro’s arbitrary module/framework/data imports, database/API work, and its full TypeScript frontmatter language are explicitly unsupported; do not infer them from Astro’s broader docs. |
| `await` | Astro supports awaited frontmatter in its normal component model. [component script example](https://docs.astro.build/en/basics/astro-components/#the-component-script) | In Sikka, awaited Frontmatter is valid **only** for a Streaming render. A synchronous Render must fail with a clear diagnostic that names Frontmatter `await` and directs callers to streaming. Test the same Template succeeds by Streaming render and fails synchronously before producing successful Rendered HTML. | Astro’s general async component/data model does not expand Sikka beyond this one documented Streaming exception. |
| Sync/Streaming semantics | Astro’s on-demand renderer streams HTML chunks in document order as components render. [Astro HTML streaming](https://docs.astro.build/en/guides/on-demand-rendering/#html-streaming) | Except for the explicitly rejected synchronous `await` Frontmatter case, sync and Streaming renders produce byte-equivalent Rendered HTML for the same Template, Props, and Slots. Streaming may partition that HTML into chunks, but preserves source order, flushes static content, and waits/yields at Component boundaries; chunk boundaries are not HTML semantics. Test equality across expressions, attributes, directives, Slots, Components, and a Streaming async-Frontmatter fixture. | Astro HTTP headers, adapters, server islands, and browser/network timing are not Sikka APIs. |

## Evidence limits

This research deliberately does not convert silent Astro implementation details into universal facts. In particular, no retrieved official Astro document/source states a general public ordinary-attribute direct/spread collision rule or exhaustively specifies coercion of all JavaScript expression values. Those rows label the selected deterministic rule as a **Sikka 1.0 contract** rather than attributing it to Astro. That sharp distinction is necessary for #6’s self-contained contract.
